## 一、首屏加载优化

### 1.1 核心逻辑链路

```
用户访问 URL
  → DNS 解析
  → TCP 连接
  → 发送 HTTP 请求
  → 服务器处理并返回数据
  → 浏览器解析HTML并请求关键资源（CSS/首屏JS）
  → 构建 DOM / CSSOM
  → 合成渲染树
  → 布局 (Layout)
  → 绘制 (Paint)
  → 页面可见
```

> **优化本质**：缩短这条链路上的每一环耗时，或提前执行关键步骤。

2.3、**预连接**（preconnect）：

完整连接流程（HTTPS）：
  DNS 查询 → TCP 三次握手 → TLS 握手（1~2 RTT） → 发送请求

preconnect 效果：
  页面加载时 → 浏览器提前完成以上全部步骤
  需要时 → 直接发送 HTTP 请求（省去 1~3 个 RTT）

```

  <link rel="preconnect" href="https://fonts.gstatic.com" crossorigin>
  
  <!-- 预连接 API 网关 -->

  <!-- 预连接 WebSocket 服务 -->
```

## 二、缓存优化

### 2.1 核心逻辑链路

```
请求资源
  → 检查强缓存（内存 / 磁盘）
      → 命中 → 直接使用（200 from cache）✅
      → 未命中 → 发起网络请求
                      → 服务器校验协商缓存
                          → 命中 → 返回 304（继续使用本地）✅
                          → 未命中 → 返回 200（返回新资源）
```

> **优化本质**：尽可能命中强缓存，避免网络请求；配合内容哈希实现永久缓存。

### 2.2 具体策略与逻辑

#### ① 强缓存

```http
Cache-Control: max-age=31536000, immutable
```

- 应用于带 `contenthash` 的静态资源（JS / CSS / 图片）
- 浏览器不发送请求，直接读本地 → 耗时趋近于 **0ms**

#### ② 协商缓存

| 机制 | 请求头 | 响应头 | 逻辑 |
| :--- | :--- | :--- | :--- |
| ETag | `If-None-Match: "abc123"` | `ETag: "abc123"` | 服务器对比内容哈希 → 一致则返回 304 |
| Last-Modified | `If-Modified-Since: Wed, 01 Jan 2025 00:00:00 GMT` | `Last-Modified: Wed, 01 Jan 2025 00:00:00 GMT` | 服务器对比修改时间 → 未修改则返回 304 |

> 协商缓存仍需一次 HTTP 请求，但省去了响应体的下载。

#### ③ 文件名哈希（缓存失效策略）

```javascript
// webpack / vite 配置
output: {
  filename: '[name].[contenthash:8].js',
}
```

| 场景 | 结果 |
| :--- | :--- |
| 内容不变 | hash 不变 → URL 不变 → 永久命中强缓存 |
| 内容变化 | hash 变化 → URL 变化 → 浏览器自动请求新资源 |

#### ④ Service Worker

```javascript
// 注册 Service Worker
navigator.serviceWorker.register('/sw.js');

// sw.js 中的缓存策略示例
self.addEventListener('fetch', (event) => {
  // Cache First 策略
  event.respondWith(
    caches.match(event.request).then((cached) => {
      if (cached) return cached;           // 命中缓存，直接返回
      return fetch(event.request).then((response) => {
        // 异步更新缓存
        caches.open('v1').then((cache) => cache.put(event.request, response.clone()));
        return response;
      });
    })
  );
});
```

- 拦截请求 → 优先读 SW 缓存 → 完全离线可用
- 彻底摆脱网络依赖，实现真正的"秒开"

#### ⑤ 存储层缓存

| 方案 | 适用场景 | 容量 |
| :--- | :--- | :--- |
| LocalStorage | 小体积配置、Token | ~5MB |
| SessionStorage | 会话级临时数据 | ~5MB |
| IndexedDB | 大量结构化数据（如离线文章列表） | 无硬限制 |

> 二次打开直接读本地数据渲染 → 减少接口请求，甚至实现"秒开"。

## 三、渲染优化

### 3.1 核心逻辑链路

```
用户操作
  → 触发事件
  → JS 执行（可能操作 DOM）
  → 样式计算 (Style)
  → 布局 (Layout / Reflow)
  → 绘制 (Paint)
  → 合成 (Composite)
  → 屏幕更新
```

> **优化本质**：减少主线程负担，避免强制同步布局，跳过不必要的重排重绘，利用合成层。

### 3.2 具体策略与逻辑

#### ① 减少重排重绘

**问题代码（布局抖动）：**

```javascript
// ❌ 逐条读写 → 强制同步布局
for (let i = 0; i < 100; i++) {
  const height = element.offsetHeight;  // 读 → 强制刷新布局队列
  element.style.height = height + 10 + 'px';  // 写 → 再次触发布局
}
```

**优化代码（批量读写）：**

```javascript
// ✅ 先统一读，再统一写
const heights = [];
for (let i = 0; i < 100; i++) {
  heights.push(element.offsetHeight);  // 批量读
}
for (let i = 0; i < 100; i++) {
  element.style.height = heights[i] + 10 + 'px';  // 批量写
}
```

| 手段 | 说明 | 逻辑链路解析 |
| :--- | :--- | :--- |
| 批量读写 DOM | 先统一读几何属性，再统一写样式 | 避免"布局抖动" → 浏览器一次性计算布局 |
| DocumentFragment | 批量插入 DOM 节点 | 减少 DOM 操作次数 → 减少重排次数 |
| class 切换 | 用 `classList.add/remove` 替代逐条改 style | 浏览器可批量处理样式变更 |

**DocumentFragment**（文档片段）：可以简单理解为存在于内存中的“轻量级 DOM 容器”。

DocumentFragment 不属于主 DOM 树。在它上面进行任意多的节点增删改，都不会触发页面的渲染和回流。
当你把所有节点都在这个“容器”里拼装完毕后，只需一次性把它挂载到真实的 DOM 上。

#### ② CSS 触发器优化

```css
/* ❌ 触发 Layout + Paint */
.box {
  position: absolute;
  top: 0;
  left: 0;
  width: 100px;
  height: 100px;
}

/* ✅ 仅触发 Composite */
.box {
  transform: translate(0, 0);
  opacity: 1;
}
```

> `transform` 和 `opacity` 仅触发合成 → 不触发 Layout 和 Paint → 主线程无阻塞。

#### ③ 事件节流防抖

```javascript
// 节流：scroll 事件每 100ms 最多执行一次
function throttle(fn, delay) {
  let last = 0;
  return (...args) => {
    const now = Date.now();
    if (now - last >= delay) {
      fn.apply(this, args);
      last = now;
    }
  };
}

window.addEventListener('scroll', throttle(() => {
  // 处理逻辑
}, 100));

// 使用 requestAnimationFrame 合并 DOM 写操作
let ticking = false;
window.addEventListener('scroll', () => {
  if (!ticking) {
    requestAnimationFrame(() => {
      updateHeader();  // 统一更新 DOM
      ticking = false;
    });
    ticking = true;
  }
});
```

> 降低 JS 执行频率 → 减少主线程阻塞 → 浏览器能按时渲染下一帧。

#### ④ 长列表优化（虚拟列表）

```
┌─────────────────────────┐
│   可视区域（渲染 10 条）  │  ← 只渲染可见的 DOM 节点
├─────────────────────────┤
│                         │
│   缓冲区（上下各 5 条）   │  ← 滚动时快速补位
│                         │
├─────────────────────────┤
│   不可见区域（不渲染）    │  ← 用占位元素撑高滚动容器
│                         │
└─────────────────────────┘
```

> DOM 节点数量从成千上万降到几十个 → 减少内存占用和渲染树构建时间。

#### ⑤ 计算分离（Web Worker）

```javascript
// main.js
const worker = new Worker('compute.js');
worker.postMessage({ data: largeArray });
worker.onmessage = (e) => {
  render(e.data.result);  // 主线程只负责渲染
};

// compute.js（独立线程）
self.onmessage = (e) => {
  const result = heavyCalculation(e.data.largeArray);
  self.postMessage({ result });
};
```

> 主线程只负责 UI → 不被计算阻塞 → 交互响应及时。

## 四、动画流畅

### 4.1 核心逻辑链路

```
屏幕刷新率 60Hz → 每帧 16.7ms

┌──────────────────────────────────────────┐
│  浏览器需要在 16.7ms 内完成：              │
│  JS 执行 + 样式计算 + 布局 + 绘制 + 合成   │
└──────────────────────────────────────────┘

如果某一帧的 JS 执行超过 ~50ms → 长任务 → 阻塞渲染 → 掉帧（卡顿）
```

> **优化本质**：保持每帧 JS 执行 < 16ms，或将长任务拆分并让出主线程。

### 4.2 具体策略与逻辑

#### 0️⃣开启GPU硬件加速

#### ① 长任务拆分（Time Slicing）

```javascript
// ❌ 长任务：一次性处理 10000 条数据 → 阻塞主线程
function processAll(items) {
  items.forEach(processItem);  // 可能耗时 200ms+
}

// ✅ 时间切片：每帧只处理一部分 → 让出主线程
function processInSlices(items, sliceSize = 50) {
  let index = 0;

  function processSlice() {
    const start = performance.now();

    while (index < items.length) {
      processItem(items[index]);
      index++;

      // 如果本帧已用超过 5ms，让出主线程
      if (performance.now() - start > 5) {
        requestIdleCallback(processSlice);  // 或 setTimeout(processSlice, 0)
        break;
      }
    }
  }

  processSlice();
}
```

```
时间线：
┌─────┐     ┌─────┐     ┌─────┐     ┌─────┐
│任务A │ 渲染 │任务B │ 渲染 │任务C │ 渲染 │ ...
└─────┘     └─────┘     └─────┘     └─────┘
 5ms         16ms  5ms   16ms  5ms   16ms
```

> 每帧 JS 执行 < 16ms → 浏览器按时渲染 → 不丢帧。

#### ② 利用 rAF 对齐帧率

```javascript
// ✅ 动画逻辑写在 requestAnimationFrame 回调中
function animate() {
  element.style.transform = `translateX(${position}px)`;
  position += 2;
  requestAnimationFrame(animate);
}
requestAnimationFrame(animate);

// ❌ 使用 setTimeout 做动画 → 与渲染节奏不同步 → 容易丢帧
setInterval(() => {
  element.style.left = position + 'px';  // 还可能触发 Layout
  position += 2;
}, 16);
```

> rAF 在浏览器每一帧的"绘制前"执行 → 与渲染节奏同步 → 避免丢帧。

#### ③ CSS / WAAPI 动画

```css
/* CSS 动画 → 浏览器可交给合成线程 */
.box {
  transition: transform 0.3s ease, opacity 0.3s ease;
}
.box:hover {
  transform: scale(1.1);
  opacity: 0.8;
}
```

```javascript
// Web Animations API → 同样由合成线程处理
element.animate([
  { transform: 'translateX(0)' },
  { transform: 'translateX(100px)' }
], {
  duration: 300,
  easing: 'ease-in-out'
});
```

> 合成线程独立于主线程 → 即使 JS 卡顿动画也流畅。

#### ④ Web Worker 计算密集型动画

```javascript
// worker.js：物理引擎计算
self.onmessage = (e) => {
  const { particles, deltaTime } = e.data;
  // 复杂物理计算（碰撞检测、引力模拟等）
  const updated = simulatePhysics(particles, deltaTime);
  self.postMessage({ particles: updated });
};

// main.js：主线程只负责应用 transform
worker.onmessage = (e) => {
  e.data.particles.forEach((p, i) => {
    // 仅触发 Composite，不触发 Layout
    particleElements[i].style.transform =
      `translate(${p.x}px, ${p.y}px) scale(${p.size})`;
  });
};
```

> 计算不占主线程 → 主线程只做轻量 DOM 更新 → 保证 60fps。

#### ⑤ 避免强制同步布局

```javascript
// ❌ 强制同步布局（Forced Synchronous Layout）
function resizeAll() {
  for (let i = 0; i < elements.length; i++) {
    elements[i].style.width = elements[i].offsetWidth + 10 + 'px';
    // 读(offsetWidth) → 写(style.width) → 读 → 写 ...
    // 浏览器被迫在每次循环中都刷新布局队列
  }
}

// ✅ 先读后写，批量操作
function resizeAll() {
  const widths = elements.map(el => el.offsetWidth);  // 批量读
  elements.forEach((el, i) => {
    el.style.width = widths[i] + 10 + 'px';  // 批量写
  });
}
```

> 避免浏览器被迫立即刷新布局队列 → 防止无谓的性能损耗。

## 五、总结

### 性能优化的"第一性原理"

| 维度 | 核心矛盾 | 解决思路 |
| :--- | :--- | :--- |
| **首屏加载** | 网络延迟 + 资源体积 | 减体积、短链路、预渲染 |
| **再次打开** | 重复请求 + 重复计算 | 缓存为王，分层缓存策略 |
| **操作顺滑** | 主线程阻塞 + 频繁重排 | 批量操作、跳过布局、虚拟渲染 |
| **动画流畅** | 长任务占用帧时间 | 拆分任务、让出主线程、使用合成线程 |

### 优化策略速查表

```
┌──────────────────────────────────────────────────────────┐
│                   前端性能优化全景图                        │
├──────────┬───────────────────────────────────────────────┤
│  加载优化  │  压缩 → CDN → 预解析 → 关键 CSS → SSR/SSG     │
├──────────┼───────────────────────────────────────────────┤
│  缓存优化  │  强缓存 → 协商缓存 → 哈希命名 → SW → 存储层    │
├──────────┼───────────────────────────────────────────────┤
│  渲染优化  │  批量读写 → CSS 触发器 → 节流防抖 → 虚拟列表    │
├──────────┼───────────────────────────────────────────────┤
│  动画优化  │  时间切片 → rAF → CSS/WAAPI → Worker → 避布局  │
└──────────┴───────────────────────────────────────────────┘
```

> **记住**：性能优化不是一蹴而就的，需要在实际项目中持续监控（Lighthouse / Web Vitals）、测量（Performance API）、迭代。
> 先测量，再优化，避免过早优化（Premature Optimization）。





## 六、核心指标

**Core Web Vitals**：Google 定义的核心网页指标

```
┌─────────────────────────────────────────────────────────────────┐
│                    用户体验三大维度                               │
├──────────────────┬──────────────────┬───────────────────────────┤
│     加载          │     交互          │     视觉稳定性            │
│  (Loading)       │  (Interactivity)  │  (Visual Stability)       │
├──────────────────┼──────────────────┼───────────────────────────┤
│  LCP             │  INP             │  CLS                     │
│  Largest Content │  Interaction     │  Cumulative Layout        │
│  ful Paint       │  to Next Paint   │  Shift                   │
│  (最大内容绘制)   │  (交互到下次绘制)  │  (累积布局偏移)            │
└──────────────────┴──────────────────┴───────────────────────────┘
```

测量方法：web-vitals库、Chrome DevTools Performance、Lighthouse、JSperformace语法



| **指标** | **良好 (Green)** | **需要改进 (Yellow)** | **差 (Red)** | **权重** |
| :------- | :--------------- | :-------------------- | :----------- | :------- |
| **LCP**  | ≤ 2.5s           | ≤ 4.0s                | > 4.0s       | 加载     |
| **INP**  | ≤ 200ms          | ≤ 500ms               | > 500ms      | 交互     |
| **CLS**  | ≤ 0.1            | ≤ 0.25                | > 0.25       | 稳定性   |



首屏加载指标：

- FP（First Paint 首次绘制）
- FCP（First Contentful Paint 首次内容绘制）：FP 到 FCP 中间其实主要是 SPA应用js执行，太慢就会导致**白屏**时间太长
- FMP（First Meaningful Paint 首次有效绘制）：主要内容呈现时间
- LCP(Largest Contentful Paint 最大内容绘制)：
- TTL：可交互时间
- TBT（Total Blocking Time）：总阻塞时间，从 FCP 到 TTL

#### 7.1 UI设计（不同设备）

①**加载反馈**：加载页面或用户操作时的反馈

加载页面：骨架屏

②**异常反馈**：系统遇到异常时，给用户的反馈

③**兜底渲染**：当预期不满足时，执行默认动作，如异常提示、空数据兜底

④**响应式设计**：前端页面出现在不同尺寸的设备上，适配不同尺寸

css媒体查询，js计算（弹窗位置变化，监听resize事件）

## 八、常见面试问题

8.1 白屏：FP 到 FCP 中间（白屏时间）其实主要是 SPA应用js执行，太慢就会导致**白屏**时间太长

#### 按「发生时机」划分：**首屏白屏** vs **运行时白屏**

**1.首屏白屏（首次加载白屏）****

- **定义**：从用户打开页面到首次渲染出有效内容之间的空白阶段，发生在页面初始化加载全过程中。
- **特点**：问题出在页面从 0 到 1 的构建阶段，是白屏问题的高发场景；既可能是 “**加载失败导致的永久空白**”，也可能是 “**加载慢导致的长时间空白**”。
- **典型诱因**：HTML / 入口资源加载失败、入口 JS 执行报错；SPA 客户端渲染的天然空白期、资源体积过大加载缓慢等。

**2.运行时白屏（交互后白屏）**

- **定义**：页面已经正常渲染出有效内容后，在用户操作、路由切换、数据更新、后台任务执行等场景下，突然变为空白状态。
- **特点**：页面曾经正常渲染过，问题出在运行时逻辑，而非初始加载链路；通常和组件渲染崩溃、状态异常、主线程阻塞强相关。
- **典型诱因**：组件渲染报错且无错误边界、路由死循环、主线程长任务卡死、内存溢出导致渲染进程崩溃、数据异常触发渲染逻辑崩溃等。

按「持续时长与最终结果」划分：**永久性白屏** vs **长时间白屏**

**3.永久性白屏（致死性白屏）**

- **定义**：页面始终无法渲染出有效内容，用户不主动刷新、不做人工干预就会一直保持空白，属于严重的功能故障。
- **本质**：页面渲染链路彻底断裂，无法自行恢复。
- 常见场景：
  - HTML 文档、入口 JS、核心 CSS 加载失败（404/500 / 跨域拦截 / CSP 阻止）
  - 入口代码存在语法错误、根组件挂载完全失败
  - 页面重定向死循环、浏览器安全策略完全阻断脚本执行
- **特点**：同一环境下稳定复现，属于最高优先级的线上事故。

**4.长时间白屏（可恢复白屏）**

- **定义**：页面最终能够渲染出有效内容，但空白停留的时间远超正常体验阈值（业界通常以 `FCP > 3s` 为判定标准），属于性能体验问题。极端弱网、低端机场景下，过长的白屏会被用户感知为 “页面卡住了 / 白屏了”。
- **本质**：渲染链路没有断裂，但某一阶段耗时过长，导致内容渲染延迟。
- 常见场景：
  - 大体积 Bundle 加载缓慢、弱网环境下资源加载延迟高
  - 主线程长任务阻塞渲染、首屏接口串行请求等待数据
  - 未做骨架屏 / Loading 兜底，初始空白期感知强烈
- **特点**：最终会呈现内容，时长随网络、设备环境波动，属于性能优化范畴。

```js
· **发生时机**：是打开页面立刻白屏，还是进行某个操作（切换路由、点击按钮、提交数据）后才白屏？

DevTools 零侵入快速初筛
1. Console 控制台：优先看错误
查看是否存在 **红色报错**，重点识别三类错误：
- 语法 / 运行时错误（`SyntaxError` / `ReferenceError` / `TypeError`）：直接定位代码执行崩溃点
- 资源加载错误（`Failed to load resource`）：标记加载失败的文件路径
- 安全策略错误（CSP 拦截、混合内容拦截、跨域错误）：标记安全层面的阻断原因
2.Network 网络面板：看资源链路
勾选「Disable cache」刷新页面（或复现操作），确认：
- 核心资源（HTML 文档、入口 JS、核心 CSS）的状态码是否为 200，有没有 4xx/5xx / 请求取消
- 资源加载的瀑布流顺序，是否存在串行阻塞、单个资源耗时过长
3.Elements 元素面板：看 DOM 是否真实存在
检查`<body>`和页面根节点（`#app` / `#root`）下是否有子 DOM 节点：
- 有节点但页面空白：属于**渲染层问题**（样式隐藏、渲染异常）
- 无节点 / 根节点为空：属于**渲染逻辑未执行 / 执行失败**（JS 崩溃、组件未挂载）
同时检查根元素是否被设置了`display: none`、`opacity: 0`、`height: 0`、`visibility: hidden`等隐藏样式。
4. Performance 性能面板：看是否阻塞 / 卡顿
录制白屏全过程，重点确认：
- 是否存在超过 50ms 的**长任务（Long Task）**阻塞主线程，导致渲染暂停
- `FCP（首次内容绘制）`的时间点，判断白屏时长和卡顿阶段
- 渲染线程、JS 线程的状态，是一直在执行还是已经停滞
```

1.**资源层排查：解决「拿不到资源」的问题**

- 加载失败：检查资源路径是否正确、CDN 是否可用、跨域配置是否正常、服务端是否返回异常
- 加载过慢：检查资源体积是否过大、是否开启压缩、是否做了代码分割、加载顺序是否阻塞渲染
- 被拦截：检查 CSP 策略、混合内容规则、浏览器安全设置是否拦截了关键资源

**2. 脚本执行层排查：解决「JS 跑不起来 / 跑崩了」的问题**

- 执行崩溃：根据报错栈定位具体代码行，检查是否有空值引用、类型错误、语法不兼容、栈溢出
- 执行阻塞：检查是否有大计算量同步逻辑、死循环、批量 DOM 操作，导致主线程被占满无法渲染
- 异常未捕获：检查异步回调、Promise、定时器中的错误是否未被捕获，导致后续逻辑中断

3. **框架层排查：解决「组件 / 路由渲染不出来」的问题**

- 检查根组件是否挂载成功，组件渲染阶段是否报错且未被错误边界捕获
- 检查路由逻辑：是否存在路由匹配失败、路由守卫死循环、重定向异常、异步组件加载失败
- 检查状态管理：全局状态更新是否触发异常副作用、是否存在循环更新导致渲染崩溃

4. **渲染层排查：解决「DOM 存在但看不见」的问题**

- 样式排查：根元素是否被设置隐藏样式、是否存在层级覆盖、是否有脱离文档流的元素遮挡
- 渲染异常：检查是否使用了触发浏览器渲染 bug 的 CSS 属性、是否硬件加速异常、是否重排重绘过度
- 容器异常：移动端 WebView 检查是否渲染进程被回收、初始化失败

5. **数据层排查：解决「数据异常导致渲染崩溃」的问题**

- 接口数据是否返回空值、异常格式、循环引用，触发渲染逻辑报错
- 数据量是否过大，导致一次性渲染 / 计算压力过高
- 数据更新逻辑是否异常，导致状态死循环、重复渲染
