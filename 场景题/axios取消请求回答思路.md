# 前端面试官：axios 是否可以取消请求？如何实现？

> 请求层封装必考题的完整回答思路

---

## 一、为什么这是一道"必考题"

面试官考的不是你**会不会调用一个 cancel 方法**，而是你有没有**处理过真实项目里的请求异常场景**——重复请求、路由切换、内存泄漏、数据覆盖，这些问题 90% 的项目都有。

**踩坑典型回答（反面教材）：**
- "能啊，用 cancelToken 创建个 source，把 token 传进请求，调用 source.cancel 就取消了"
- 追问"cancelToken 从哪个版本开始废弃？官方推荐什么方式？" → "啊？废弃了？我一直用 cancelToken 啊"
- 追问进阶场景（重复请求、路由切换、取消后后端是否执行、错误区分）→ "我平时就是单个请求手动取消，这些封装没做过"

**本质问题：**
- 用了好几年 Axios 取消请求，只知道 cancelToken，连官方废弃了都不知道；
- 只会取消单个请求，没封装过生产级自动取消逻辑；
- **能把这个问题讲透，才算真的会封装请求层。**

---

## 二、完整回答框架：五层讲透

把取消请求做扎实，分 **5 层**往下讲，一层比一层接近生产实践。

### 第 1 层：搞对 API，别用已经废弃的 cancelToken

很多人学 Axios 时学的就是 cancelToken，用到现在都不知道早废弃了。

- **从 Axios v1.0 起，官方废弃了 cancelToken**，推荐用标准的 **AbortController**，和 fetch 的取消方式完全统一；
- 用法很简单：
  - 创建 `AbortController` 实例；
  - 把 `controller.signal` 传给请求的 `signal` 参数；
  - 要取消时调用 `controller.abort()`；
- 这是 **Web 标准 API**，不只是 Axios，所有支持 `signal` 的请求库都能用，以后不会再变——别再抱着 cancelToken 不放了。

### 第 2 层：搞懂取消的本质，别以为取消后后端就不执行了

很多人有个误区：以为调用了 abort，请求就没发出去、后端就不执行了。**错。**

- Axios 取消的本质是**客户端中断连接**：底层调用 `XMLHttpRequest.abort()` 或 fetch 的 signal 中断，只是浏览器不再接收响应了；
- 但只要请求已经发出，**后端该执行还是会执行**；
  - 例：调用删除接口发出后取消，后端可能已经把数据删了——取消不代表操作没发生；
  - 所以**写操作的接口不要随便取消**；
- 取消后浏览器会把请求标记为 `canceled`，**不触发成功回调，但会触发错误回调**——这个错误要特殊处理，不能当成接口报错。

### 第 3 层：自动取消重复请求，解决数据覆盖的核心封装

这是实际项目最常用的场景：用户快速切换筛选条件或连点提交按钮，上一个请求没回来，下一个又发了。网络不好时**后发的先回来、先发的后回来**，把新数据覆盖成旧数据，页面数据乱跳。

**解决方案——封装请求 map：**
- key = 请求方法 + URL + 参数序列化后的字符串；
- 发请求前先查 map 里有没有相同 key 的 pending 请求，**有就先 abort 取消上一个**，再把当前请求的 cancel 存入 map；
- 请求结束（成功失败都算）后，从 map 里删掉；
- 这样同一个接口永远只有最新的请求生效，旧请求直接被取消，不会出现数据覆盖。

**注意：自动取消只适合幂等的 GET 请求**。POST 提交、支付等写请求不要自动取消，要做**按钮 loading 禁用**，防止重复提交。

### 第 4 层：路由切换批量取消，解决内存泄漏的必做项

这个 90% 的项目都漏了：用户在列表页发了五六个接口还没回来，直接切到详情页，这些请求还在 pending。不仅占带宽，请求回来时组件已卸载，还在尝试更新状态——**轻则控制台报警告，重则内存泄漏**。

**解决方案：**
- 在**路由前置守卫**里遍历请求 map 里所有 pending 请求，全部 abort 取消，然后清空 map，保证切路由后没有任何遗留请求；
- 组件卸载时，如果有当前组件特有的长请求，也要在 `onUnmounted` 里取消，别让请求跟着组件生命周期走。

### 第 5 层：踩坑指南，别让取消请求搞出更多 bug

取消请求看着简单，坑不少：

1. **取消错误不要当成接口报错处理**
   - Axios 取消后抛 `cancel` error，fetch 抛 `AbortError`；
   - 错误拦截器里要判断错误类型，是取消错误直接 return，**不弹提示、不上报**；
   - 否则用户切个路由，弹一堆"请求失败"的提示。

2. **上传/下载取消后要重置状态**
   - 文件上传下载这类长请求取消后，要手动重置进度条、恢复按钮状态；
   - 否则用户取消后，按钮还卡在"上传中"，进度条停在一半。

3. **不要滥用自动取消**
   - 表单提交、支付、下单等写操作：自动取消可能导致用户以为没提交成功，其实后端已执行——这种要做**按钮防重点**，而不是取消请求；
   - 全局字典接口、公共配置接口：不用每次都取消，可以**做缓存复用结果**。

---

## 三、一句话总结

> 这道题考的不是你会不会调用一个 cancel 方法，而是你有没有**封装过生产级的请求层**。

- **普通开发**：只会用 cancelToken 取消单个请求，出了数据覆盖、内存泄漏的问题都不知道为啥；
- **高级工程师**：知道用标准 AbortController → 会封装自动取消重复请求 → 路由切换批量清理 → 知道取消的本质和各种坑 → 做出的请求层稳，不会有数据乱跳、内存泄漏、莫名其妙的报错。

**回答主线（背下来就能讲）：**
标准 AbortController 替换废弃 API → 讲清"取消=客户端断连、后端仍执行"的本质 → 请求 map 封装自动取消（仅幂等 GET）→ 路由守卫 + 组件卸载批量清理 → 区分取消错误、重置长请求状态、别滥用自动取消。
