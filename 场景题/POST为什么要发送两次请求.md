# 前端面试官：POST 为什么要发送两次请求？

> 一道把「跨域 + 预检请求」讲透的前端面试必答题

## 一、完整回答框架：三层讲清预检请求

先纠正一个前提：**第二次不是 POST，而是预检请求（OPTIONS）**。面试官真正想听的，是下面这三层逻辑。

视频从一个面试现场切入：

- 面试官问：「有时候发 POST，浏览器会先发一次 OPTIONS，这是为什么？」
- 候选人当场懵：「网络问题？接口写错了？」再问两句直接沉默，面试到这就结束了。
- 这道题看着偏门，其实是跨域与网络请求的核心考点；答不上来，直接说明你没吃透**浏览器同源策略**。

面试官的三连问，正好对应三层回答主线：

1. 为什么 GET 很少发两次，POST 却经常发？
2. 什么情况下浏览器会自动发 OPTIONS？
3. 怎么优化，让它少发甚至不发？

### 第 1 层：这不是两次 POST，是预检请求

- 浏览器判断请求属于**非简单请求**时，会先发送一次 **OPTIONS** 请求；
- 这次请求是在问服务器：**我能不能跨域请求你？**
- **服务器同意了，才发真正的 POST**；不同意就直接拦截，控制台报跨域错误——真实 POST 根本不会发出去。

**为什么 GET 很少「发两次」，POST 却经常？**

- GET 通常不带自定义请求头，Content-Type 也是默认值，属于「简单请求」，浏览器直接发，不预检；
- 实际项目里的 POST 大多用于 JSON 接口：`Content-Type: application/json`、带 `token / Authorization` 等自定义头，命中非简单请求，所以必先发 OPTIONS。
- 结论：不是 POST 这个方法本身要发两次，而是 **POST 请求常带有「非简单请求」的特征**。

> 一句话说清：你在 Network 里看到的「两次请求」，是一次跨域预检 + 一次真实业务请求。

### 第 2 层：什么请求会触发预检？

只要满足任意一条，浏览器**必发 OPTIONS**：

| 触发条件 | 说明 |
| --- | --- |
| 请求方法不是 GET / POST / HEAD | 如 PUT、DELETE、PATCH 等 |
| 携带了自定义请求头 | 如 token、Authorization 等业务头 |
| Content-Type 不是「简单类型」 | 只允许 `application/x-www-form-urlencoded`、`multipart/form-data`、`text/plain`，用 `application/json` 就会触发预检 |

> 视频里把它简化成两条：请求方法不是 GET/POST/HEAD；自定义请求头（如 token、Content-Type: application/json）携带了特殊请求头字段。按规范其实还有 Content-Type 这一条，面试时讲全更加分。

### 第 3 层：怎么优化？（面试官加分项）

- **后端设置 `Access-Control-Max-Age`**：缓存预检结果，在有效期内同一请求不再重复预检；
- **尽量用简单请求格式**：减少自定义请求头，业务允许时避免不必要的 `application/json`；
- **同域部署 / 代理转发**：Nginx 反向代理、开发环境 proxy，从根源避免跨域。

很多人干了三年，只知道「跨域报错要让后端配」，却不知道浏览器还会偷偷发预检请求，一面试就露馅。

## 二、一句话总结

> 这道题考的不是背 API，而是你有没有跨域原理、浏览器机制、性能优化的真实认知。

- **普通开发**：看到 Network 里两条记录，以为「POST 发了两次」，说不清第二条到底是什么；
- **值钱的前端**：张口就讲清三层逻辑——不是两次 POST 而是预检 → 什么条件触发 → 怎么优化。

**回答主线（背下来就能讲）：**
先纠正「不是两次 POST，是一次 OPTIONS 预检 + 一次真实 POST」→ 讲触发条件（方法、自定义头、Content-Type 三条）→ 给优化方案（Max-Age 缓存预检 / 简单请求格式 / 同域部署）。
